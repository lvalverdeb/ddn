# Proposed: §9.1's transfer record cannot answer §5.3.2's priority rule

**Status:** proposal. Nothing here has been applied to
`docs/vrp-problem-definition.md`, which is **Draft v0.15**.
**Date:** 23 September 2026
**Found by:** planning Task 8 (`docs/plans/transfer-priority.md`).
**Companion:** `docs/spec-proposals/v0.16-depot-capacity.md`, independent of
this and landable in the same revision.

---

## Why this exists

§5.3.2 closes with a rule the data contract cannot support:

> **Priority.** When van capacity or van-hours are short, hub-origin loads and
> transfers compete. Both are ranked by the same priority score as delivery
> (§8.1); a transfer for an SLA-today envelope is a hard inclusion, like an
> SLA-today delivery.

§9.1's transfer-request table (`:437-443`) declares eight fields:
`transfer_id`, `package_id`, `from_facility_id`, `to_facility_id`, `reason`,
`created_at`, `deadline`, `weight_g`. **Neither a priority score nor an SLA
date is among them**, so a planner handed a transfer request can do neither
thing the paragraph asks.

The code matches the table, as it should: `circuit.choose` takes transfers in
the order the caller listed them and declines `OVER_CAPACITY` once the 500 kg
is gone. Which transfers ride is therefore decided by list position — and
since v0.15's queue landed, that quietly means "yesterday's first", a rule
nobody chose.

---

## 1. §9.1 — the transfer record gains the score

```diff
 | deadline | datetime | min(receiving depot's next morning release, SLA date) |
 | weight_g | integer | |
+| priority | number | §8.1's score for the envelope, so §5.3.2 can rank a transfer against a hub-origin load |
```

**Not derivable from what is there.** `package_id` names the envelope, but a
planner is handed transfers and a pool of hub-origin envelopes — the
transferred envelope is at a *depot*, so it is in neither. Resolving the score
would mean a second lookup beside a record §9 calls "the only schema
definition", which is the arrangement that produced `Tally.disputed`: a field
the code reads, supplied out of band, silently zero when absent.

## 2. §5.3.2's SLA-today clause describes a case §7.1 forbids

This is the substantive finding, and it is a contradiction inside the
document rather than a gap in it.

§7.1 states:

> A transfer is not raised for an envelope that cannot reach the destination
> before its SLA date; it goes to the return run instead.

§9.1 defines `deadline` as `min(receiving depot's next morning release, SLA
date)`. For an envelope whose SLA is **today**, that minimum is today — and
the transfer would arrive at the receiving depot tomorrow morning, because §5
puts line-haul on D and all delivery on D+1. So an SLA-today transfer can
never arrive in time, §7.1 refuses to raise it, and it never reaches the
ranking where §5.3.2 calls it a hard inclusion.

Measured against the code, which implements §7.1 faithfully:

| envelope's SLA | deadline | raised? |
|---|---|---|
| today | today 00:00 | **no** — already past |
| tomorrow | tomorrow 00:00 | yes |
| later | tomorrow 07:00 (the release) | yes |

So the clause is unreachable. Two readings, and the document should pick one:

**(a) It predates the one-day lag.** §5.3.2's Priority paragraph is v0.12's;
the lag was confirmed in v0.10 but the *delivery* consequence — that a
transfer raised tonight can only help an envelope due tomorrow or later — was
never carried back into it. On this reading the clause should read **"a
transfer for an envelope due at the receiving depot's next morning release"**,
which is the earliest SLA a transfer can still serve, and is what "like an
SLA-today delivery" means one stage upstream.

**(b) It means something §7.1 should permit.** If operations genuinely wants
an SLA-today envelope moved — to be delivered late rather than returned —
then §7.1's bullet is the one to change, and §6.1's expiry clock has to say
what happens when it arrives after its date.

**Recommendation: (a).** It makes the two sections agree, it needs no change
to §7.1 or §6.1, and it is the reading the arithmetic already implements.

```diff
-**Priority.** When van capacity or van-hours are short, hub-origin loads and transfers compete. Both are ranked by the same priority score as delivery (§8.1); a transfer for an SLA-today envelope is a hard inclusion, like an SLA-today delivery.
+**Priority.** When van capacity or van-hours are short, hub-origin loads and transfers compete. Both are ranked by the same priority score as delivery (§8.1); a transfer whose envelope is due on the receiving depot's next morning release is a hard inclusion, as an SLA-today delivery is at §6.1. A transfer for an envelope due *today* is not raised at all (§7.1): line-haul runs on D and delivery on D+1, so it could not arrive in time.
```

Under (a), **no `sla_date` field is needed.** The deadline already carries it
in the only form the rule uses: a transfer is a hard inclusion exactly when
its `deadline` is the receiving depot's next morning release *and* the SLA
date is what set that minimum — which is the case a planner can read off
`deadline` alone once the clause names the release rather than "today".

## 3. What this unblocks

`docs/plans/transfer-priority.md`, which is otherwise stalled: ranking
transfers against hub-origin loads by §8.1, and the hard inclusion. e2e-2's
row B4 ("Dropped loads are the lowest-priority; every SLA-today transfer and
envelope is carried") currently asserts only that the roll reason is `no van`,
because its first two clauses have no implementation to test.

Nothing is built until this lands. §9 is "the only schema definition" and a
planner cannot read a field the table does not declare — which is the same
rule that kept `lastmile.py`'s `UNREACHABLE_ADDRESS` deleted rather than
wired, and it is the right way round.

## What this proposal does not ask for

- **No `sla_date` field**, under reading (a). If you take (b), it is needed,
  and so is a §6.1 answer about arrival after the date.
- **No change to §7.1.** Under (a) its bullet is already correct and is what
  the contradiction resolves *to*.
- **Nothing about van-hours.** §5.3.2's "or van-hours are short" is the other
  half of the shortage and §8.3 computes van-hours over a day, not a night.
  Separate gap, separate proposal.
