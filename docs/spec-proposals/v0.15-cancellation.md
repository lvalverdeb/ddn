# Proposed: the Cancelled outcome

**Status:** proposal. Nothing here has been applied to
`docs/vrp-problem-definition.md`, which remains **Draft v0.14**.
**Date:** 22 September 2026
**Audience:** the author of the problem definition.
**Companion:** `docs/spec-proposals/v0.15.md`, which is independent of this and
can land in the same revision. Neither depends on the other.

---

## Why this exists

`docs/e2e/e2e-3-depot-delivery-and-outcomes.md` §2.2 defines a case the parent
does not have — **a customer withdraws an envelope before it is delivered** —
and marks it for promotion. §6's outcome table has four rows and none of them
is this; §5.2.6's diagram does not draw it; §13.2's Envelopes row does not
accept the event. The slice cannot be built until the document says what the
case is, because `tests/test_model.py:143` parses §5.2.6's own diagram and
refuses any `Status` the document does not name. That is the right way round,
and it is why this is a spec change rather than a code change.

**On the version.** e2e-3 §2.2 says *"[Promote to parent §5.2.6 and §6 as
v0.14.]"* and `docs/claude-code-task-prompts.md` asks for a file named
`v0.14-cancellation.md`. Both were written while the parent was v0.13. The
parent is now **v0.14** — §8.2's `excluded_by_ops` landed under that heading —
so the target here is **v0.15** and the file is named for it. Flagging rather
than silently renaming.

## 1. First, a word that already means three things

This is the part worth settling before any of the text below.
"Cancel" appears in the document now in two senses, and this proposal adds a
third:

| § | What is cancelled | Consequence today |
|---|---|---|
| §5.1.7 | a **pickup request**, after the van was dispatched | "Stop removed at next cycle." |
| §5.2.6, §13.2 | a **transfer**, before it is carried | `Transfer requested → Ready`; `POST /transfers/{id}/events` (cancelled) |
| *proposed* | an **envelope**, before it is delivered | → return run |

Three different objects, one verb, and the second and third both end with an
envelope changing status — so "the envelope was cancelled" is already ambiguous
in a way that will reach an incident report. `ddn/api/routers/transfers.py`
takes a `cancelled` event today and `ddn/api/routers/envelopes.py` would take
another.

**Recommendation: name the new one `Cancelled` and rename neither of the
others, but say in §2's glossary which is which.** Proposed glossary entry:

```markdown
**Cancelled** — of an *envelope*: withdrawn by the customer before delivery
(§6). Of a *transfer*: abandoned before it is carried, leaving the envelope at
its current depot (§5.3.2). Of a *pickup request*: withdrawn before collection
(§5.1.7). The three are distinct events on distinct entities and only the first
is a §6 outcome.
```

If you would rather disambiguate at the source, the alternative is
**`Withdrawn`** for the envelope case, which collides with nothing. The code
has no preference; the vocabulary test (`tests/test_contract.py`) pins whatever
§6 and §9.2 spell.

## 2. §6 — the outcome table, and a modelling question first

**The question.** §6 is headed *"Delivery outcomes and their consequences"*,
and its four rows are all results of an **attempt**: someone went to the door.
A cancellation is not — nobody attempted it, and in the common case the
envelope never left the facility. Putting it in that table makes it an outcome
of an attempt in every reading of the document and in
`ddn/model/outcomes.py`, which asks "what happened at the doorstep" once per
attempted envelope.

Two ways to resolve it, and this needs your decision rather than my guess:

**(a) A fifth row, with the definition carrying the distinction.**
Simplest, and it keeps one table for "how an envelope stops being deliverable".

```diff
 | **Postponed** | Attempt not completed (recipient unavailable, incorrect address, driver out of time…). | Held at facility in Ready state. | Retried while SLA date not passed. … |
+| **Cancelled** | Withdrawn by the customer before delivery. Not the result of an attempt: it may arrive at any time up to the moment of delivery. | Back to facility if not there already, then customer via return run. | Removed. |
```

**(b) A new §6.2, "Withdrawal before delivery"**, leaving §6's table to mean
attempts only. More faithful to what the day actually does, at the cost of a
reader having to find two places.

I recommend **(a) with the definition doing the work**, because §6's last
column — "Effect on next day's pool" — is the question operations actually
asks, and a cancellation answers it the same way a rejection does.

## 3. §5.2.6 — one edge already exists, and one does not

e2e-3 §2.2 asks for a single edge: *"Lifecycle edge: Ready → Return run
(cancelled)."* **That edge is already drawn.** §5.2.6 has
`Ready → Return run (SLA date passed without delivery)`, and
`ddn/model/lifecycle.py` permits `Ready → Return run` today. What is missing
there is only a second *reason* on an existing arrow.

**The edge that genuinely does not exist is the one the slice document's own
second bullet needs.** e2e-3 §2.2 says:

> If it is on an active route, the driver is notified at the next plan refresh;
> the stop is removed if not yet visited.

An envelope on an active route is **Dispatched**. §5.2.6 draws
`Dispatched → {Delivered | Rejected | Returned | Postponed}` and nothing else —
no edge back to Ready, and no edge to Return run. So a cancellation after
dispatch has nowhere legal to go, and the slice as written cannot be
implemented without either inventing an edge or recording a postponement that
did not happen. Verified against the code: `may(DISPATCHED, RETURN_RUN)` is
`False` and `may(DISPATCHED, READY)` is `False`.

Proposed diagram change — two lines, not one:

```diff
    → Ready → Return run (SLA date passed without delivery)
+   → Ready → Return run (cancelled by the customer)
+   → Dispatched → Return run (cancelled by the customer while on a route, stop not yet visited)
    → Rejected / Returned / SLA expired: Return run → Returned to customer
```

and the last line gains the new reason:

```diff
-   → Rejected / Returned / SLA expired: Return run → Returned to customer
+   → Rejected / Returned / Cancelled / SLA expired: Return run → Returned to customer
```

**Delivered stays terminal, and that is the refusal.** §5.2.6 draws nothing out
of Delivered, so a cancellation arriving after the stop was visited is an
illegal transition, which §13.1 already says is `409` with the current state.
No new rule is needed for e2e-3 §2.2's third bullet — the existing one covers
it, and `TRANSITIONS[Status.DELIVERED]` is already empty.

## 4. §13.2 — the event

```diff
-| Envelopes | `POST /envelopes/batch` (upload-file ingest); `GET /envelopes/{id}`; `POST /envelopes/{id}/events` (outcome, address correction) | §5.1.1, §6, §9.1 |
+| Envelopes | `POST /envelopes/batch` (upload-file ingest); `GET /envelopes/{id}`; `POST /envelopes/{id}/events` (outcome, address correction, cancellation) | §5.1.1, §6, §9.1 |
```

§13.1 already requires that "overrides and outcome events record the actor and
time", so a cancellation carries who asked for it without any §9.1 change —
**provided §6 makes it an outcome (option (a) above).** Under option (b) that
sentence would have to name withdrawals too.

## 5. §11 — the metric

e2e-3 §8 lists cancellations among the slice's metrics and §11's table has no
row for them. A count is a measurement rather than a commitment, so this one
can be added without inventing a target:

```diff
+| Cancellation rate | Envelopes cancelled ÷ envelopes Ready | [TBD] | §6 |
```

The `[TBD]` is deliberate and belongs to the same never-fill list as §11's ten
other targets: `docs/assumptions.md` records why a target is a customer promise
and not an input.

## 6. What lands in code once this is approved, and in what order

Nothing below is written yet. Listed so the size of the change is visible.

1. `ddn/model/lifecycle.py` — `Status.CANCELLED` is **not** needed. Cancellation
   is a reason for reaching `Return run`, not a status an envelope rests in;
   adding one would give §5.2.6 a state with exactly one way in and one way
   out. What is needed is the two new edges of §3 and a fifth member of
   `records.Outcome`.
2. `ddn/model/outcomes.py` — `AFTER_ATTEMPT` gains a row, and `record` grows a
   branch for an outcome that produces no attempt. This is the one place where
   option (a) versus (b) changes the shape of the code rather than the prose.
3. `ddn/lastmile/` — remove a not-yet-visited stop from an active route; refuse
   for Delivered.
4. `ddn/api/routers/envelopes.py` — the event, `409` on refusal, via the
   existing `advance`, which already validates against §5.2.6.
5. `ddn/e2e/depot_delivery/` — row C8, and `DayOutcomes` carrying the reason.

**What enforces the order.** `tests/test_model.py:143` asserts every `Status`
the code defines appears in §5.2.6's own diagram, and `tests/test_contract.py`
asserts the code's §9.2 vocabulary is a subset of the line §9.2 publishes. So
the code *cannot* emit a reason the document does not list — which is why this
document comes first, and why `lastmile.py`'s `UNREACHABLE_ADDRESS` was deleted
rather than wired when the same situation arose (see `v0.15.md` §7).

## 7. Open questions this proposal does not answer

From e2e-3 §9, and they belong to operations rather than to the solver:

- **Can a customer cancel by API only, or also by phone via operations?** This
  decides whether the event carries an actor drawn from a customer identity or
  from an operator's, which §13.1's audit rule will then pin.
- **Is there a cut-off after which cancellation is refused even if the stop is
  not yet visited?** e2e-3 §2.2 implies none. A rider halfway to an address is
  a real cost, and §7.2's soft constraints are where such a rule would live.
- **Does a cancelled envelope count against the customer's SLA?** §11's
  compliance ratio divides by envelopes Ready; if a cancellation stays in the
  denominator, withdrawing an envelope damages the reported figure.

## What this proposal does not ask for

- **No change to §7.1, §8 or §10.** Cancellation is not a constraint, not an
  objective, and §10's worked example contains none.
- **No new §9.1 field**, under option (a).
- **No placeholder value.** Nothing here is `[TBD]` except §11's target, which
  is deliberately unfilled.
