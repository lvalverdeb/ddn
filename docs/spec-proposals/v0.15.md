# Proposed: problem definition v0.15

**Status:** proposal. Nothing here has been applied to
`docs/vrp-problem-definition.md`, which remains **Draft v0.14**.
**Date:** 19 September 2026
**Audience:** the author of the problem definition.

---

## Why this exists

Six things the code does, correctly, that the document does not describe. They
were found by the conformance audit (`docs/audit/conformance-2026-09-19.md`)
and every one was rated `PARTIAL` there for the same reason: not that the
behaviour is wrong, but that §9 says it is "the only schema definition" and
§13.1 says "the OpenAPI document is the published form of §9", and these are
published without being defined.

A seventh item is the reverse — a reason code the code *should* emit and
cannot, because §9.2's vocabulary is closed and a test enforces it.

Each section below gives the current file:line, the proposed text, and what
would break or stop breaking.

---

## 1. §9.1 — `Facility.unload_min`

**In code:** `ddn/model/records.py:272`, consumed at `:287` to derive
`latest_van_departure`.

**In the spec:** nowhere as a datum. §3.1's table derives the latest departure
as `[release − transit − unload]` and §7.4 leaves "Facility loading/unloading:
[TBD] minutes", but §9.1's Facilities line names only three additions.

This directly contradicts `records.py`'s own contract — "every field that
section declares and no other".

```diff
 **Facilities** — as §3.1, plus `transit_from_hub_min`, `route_release_time`
-and derived `latest_van_departure`.
+`unload_min` and derived `latest_van_departure`.
```

The value is a placeholder: `FACILITY_UNLOAD_MIN = 30`, registered **invented**
in `docs/assumptions.md`. §7.4's `[TBD]` is the gap it fills.

## 2. §9.1 — `Transfer.actor`

**In code:** `ddn/api/schemas.py:173`, required, consumed at
`ddn/api/routers/transfers.py:66`.

**In the spec:** §9.1's transfer-request table lists eight fields and this is
not among them. The field's own docstring cites §13.1, but §13.1's audit rule
is "Overrides (§8.2) and outcome events record the actor and time" — and
raising a transfer is neither. The justification does not reach it.

```diff
 | deadline | datetime | min(receiving depot's next morning release, SLA date) |
 | weight_g | integer | |
+| actor | string | §13.1: who raised it |
```

and, in §13.1:

```diff
-- **Audit.** Overrides (§8.2) and outcome events record the actor and time.
+- **Audit.** Overrides (§8.2), transfer requests and outcome events record the
+  actor and time.
```

## 3. §9.1 and §5.3.2 — the inter-depot transit input

**In code:** `ddn/model/travel.py:72`, `between(matrix, rows) -> Transit`. Its
docstring names the gap: "§3.1 gives transit *from the hub* and nothing between
depots, and the circuit planner declines every transfer rather than guess one."

**In the spec:** §5.3.2 describes multi-leg circuits over seven nodes with
per-load deadlines, and never says where depot-to-depot durations come from.
§3.1's table has a "Transit from hub" column only. §12 Q8 asks for hub→depot
transit for D1–D6 and nothing pairwise.

This is the one item that is a real gap in the operation's data and not just
undescribed plumbing: **a circuit cannot be timed without it**, and
`linehaul.plan` declines every transfer when it is absent rather than guessing
— which `tests/test_transfers.py` pins.

```diff
 **Facilities** — as §3.1, plus `transit_from_hub_min`, `route_release_time`
 `unload_min` and derived `latest_van_departure`.
+
+**Inter-facility transit** — seconds between any two facilities, by id. §3.1
+gives transit from the hub only, and §5.3.2's circuits call at depots in
+sequence, so the pairwise figure is a solver input in its own right. It is
+directional: the two directions of one pair are not averaged.
```

and in §12 Q8, widen "hub → depot transit time for D1–D6" to include the
pairwise matrix, **or** state that pairwise transit is derived from the §3.3
road matrix rather than supplied. The code does the latter — `travel.between`
reads the same gateway matrix §3.3 already needs — so stating it is enough.

## 4. §9.2 — the violation list, and its shape

**In code:** `ddn/api/schemas.py:244`, carried on `JobState.violations` and
`RouteRun.violations`.

**In the spec:** §13.1 states the obligation — "Every routing result carries
its §7.1 violation list (empty on success)" — and gives no shape. §9.2
describes routes, unassigned and the line-haul plan, and not this.

```diff
 - **Line-haul plan:** per van, an ordered list of legs …
+- **Violations:** per routing result, the §7.1 bullets it breaks — the bullet's
+  own text, a detail naming what breached it, and the vehicle or package
+  concerned where one applies. Empty on success (§13.1).
```

## 5. §13 — the error body

**In code:** `ddn/api/schemas.py:272`, installed app-wide at
`ddn/api/app.py:62-68` and documented into the OpenAPI responses at `:101`.
RFC 9457 shaped.

**In the spec:** §13 specifies no error body at all, while §13.1 requires that
an illegal transition is "409 with the current state" — a requirement about a
body that is never described.

Proposed as a new subsection after §13.3, since it is a transport concern
rather than a §9 entity:

```markdown
### 13.4 Errors

Failures are RFC 9457 problem documents: `title`, `detail`, `status`, plus
`current_state` and `package_id` where the failure is about one envelope. The
§5.2.6 refusal (§13.1) uses them to say where the envelope actually is; the
missing-idempotency-key refusal uses them to name the header.
```

(§13.4 "Out of scope for the API" becomes §13.5. Note `tests/test_api_contract.py`
asserts §13's subsections are numbered 13.x and that no `### 14.x` heading
exists, so the renumber is safe but the count is checked.)

## 7. §9.2 — a reason for an envelope no road reaches

**This one is a request, not a description.** The other six describe code that
exists; this one is blocked *by* the spec and the code cannot be written until
it lands.

`lastmile.reachable_subset` removes stops that have no road path to the
facility or to each other — real on OSRM data, where an address can snap to a
disconnected fragment. The pruning is necessary: `MTX-5`'s unreachable sentinel
is `-1`, the cheapest arc there is, so the solver is *drawn to* those stops and
the verifier then refuses the whole plan.

The envelopes it removes appear in **neither** §9.2 list — not in a route, not
in unassigned-with-reason. They vanish, and the totals understate the gap
because `offered` is counted after the prune.

`ddn/lastmile/plan.py` carried an `UNREACHABLE_ADDRESS = "unreachable address"`
constant for this, unemitted and in neither `REASONS` set. It has been deleted
rather than wired, because `tests/test_contract.py` parses §9.2's line out of
this document and asserts the code's vocabulary is a subset of it — so the code
cannot emit a reason the document does not list, which is the right way round.

```diff
-- **Unassigned envelopes:** package_id; reason (time / count / not ready by cut-off / low geocode confidence / SLA expired / in dispute / excluded by operations).
+- **Unassigned envelopes:** package_id; reason (time / count / not ready by cut-off / low geocode confidence / SLA expired / in dispute / excluded by operations / unreachable address).
```

With that line changed, the reporting change follows in the same commit:
`reachable_subset` returns the dropped indices alongside the kept ones, and
`plan_facility` carries them out as `Excluded` records the way `select` already
does for capacity.

## 8. §14 — put the revision history in order

§14's table ascends 0.1 → 0.6 and then **descends** 0.14 → 0.7. Rows 0.7
onward were prepended newest-first after 0.6, so the table has two sort orders
glued together and a reader scanning for the newest entry finds it in the
middle.

Reverse the 0.7–0.14 block so the whole table ascends. Nothing reads row order
— `tests/test_api_contract.py` splits on the §14 heading and checks subsection
numbering only.

While there: every row's Author column is `[TBD]`, including v0.13's and
v0.14's, which were written from the audit. Worth filling or worth removing.

## What this proposal does not ask for

- **No change to §7.1, §8 or §10.** The audit's findings against those are code
  defects, and they have been fixed in code.
- **No placeholder values.** §8's objective weights, §11's targets and the
  above are separate questions; `docs/assumptions.md` records which gaps are
  deliberately unfilled and why.
- **Nothing about the fixture.** §10's worked example is sound as of v0.13.
