# Proposed: §5.1.1 promises a slower order that §9 cannot record and §5.2.5 cannot time

**Status:** **applied** in 56e5aee. `docs/vrp-problem-definition.md` is
**Draft v0.17** and carries all six edits below. Kept as the record of what was
proposed and of §8's four questions, which approval did not settle -- question 1
in particular: `late_ready` is in §9.1 and on no record, because nothing writes
it.
**Date:** 23 September 2026
**Found by:** planning Task 17 — e2e-1 row A9, the late-file exception
(`docs/plans/t17-late-file-exception.md`).

---

## Why this exists

§5.1.1 states the exception in one sentence:

> The upload file **usually arrives before the mailbag**. […] Where the file is
> late or missing, the bag is processed in the slower order (open, key in, then
> geocode) and its envelopes are flagged as late-ready.

Three obligations, none of which §9 or §5.2.5 can meet:

1. **"Where the file is late or missing"** — no record anywhere says when a
   bag's upload file arrived, or that it never did. The mailbag table has
   `requested_at`, which is the customer's call, not the file.
2. **"processed in the slower order (open, key in, then geocode)"** — §5.2.5's
   readiness formula has no geocoding term, because it is written for the
   other case.
3. **"flagged as late-ready"** — no field carries the flag.

So the exception is prose today. A hub that is late on a file produces the same
`expected_ready_at` as one that is not, and nothing downstream can tell.

## What the code does instead

`processing.readiness.schedule` runs three stages — reconcile → assemble →
sort — and takes bag arrival times only:

```python
def schedule(envelopes, arrival_of, *, reconcile_per_hour,
             assembly_per_hour, sort_per_hour) -> tuple[Readiness, ...]
```

There is no geocode stage and no argument that could select one. That is not an
oversight: `docs/assumptions.md:76` records the reasoning, and it is correct as
far as it goes.

> Geocoding has no rate here: §5.2.2 puts it before the bag arrives in the usual
> case, so it is off the critical path for readiness.

**The usual case is the scope of that sentence, and the exception is the case it
excludes.** This proposal retires it.

`tests/e2e/test_slice_1_pickups_to_hub.py:309` is named `test_a9` and asserts
§5.2.3's clean-room rule — that an assembly envelope is ready later than a
finished one. True, tested elsewhere, and a different rule. A9 has been reading
as covered.

## 1. §9.1 — the mailbag record cannot say the file was late

```diff
 | pickup_window_start / end | datetime, optional | |
 | seal_id | string | Safety device identifier |
+| file_received_at | datetime, optional | When the customer's upload file arrived. Null where it never did — §5.1.1's "late **or missing**" |
```

Optional-with-null rather than a boolean, because the two cases §5.1.1 names are
different facts and a boolean would flatten them: a file three minutes late and
a file that never came are both "late" but only one has a time. The comparison
that matters — file against bag — is then derivable rather than asserted:

```
late = file_received_at is null or file_received_at > (bag received at hub)
```

## 2. §9.1 — the envelope record cannot carry §5.1.1's own flag

```diff
 | excluded_by_ops | boolean, optional | Operations override: force out. Not offered to the solver; reported unassigned |
+| late_ready | boolean, optional | §5.1.1: the bag's file was late or missing, so geocoding was on the critical path for this envelope |
```

**This is derivable from §1, and it is still asked for here**, for two reasons.
§5.1.1 puts the flag on the envelope — "its envelopes are flagged as
late-ready" — not on the bag. And an envelope outlives its bag in the data: once
Ready it is routable on its own, and §9.1's envelope table is what the delivery
solve and every report downstream see. `expected_ready_at` is equally computed
and sits in the same table for the same reason.

Whether the derived field earns its place is a fair question and is in §8 below,
not silently decided.

## 3. §5.2.5 — the readiness formula is stated for one case of two

The current sentence is not wrong. It is conditioned, and the other condition
has no sentence:

> **With the upload file in hand before arrival**, the expected ready time for
> each envelope can be computed at request time as: van's expected return to hub
> + reconciliation time + (assembly queue time if required) + sorting time.

```diff
-With the upload file in hand before arrival, the expected ready time for each envelope can be computed at request time as: van's expected return to hub + reconciliation time + (assembly queue time if required) + sorting time.
+With the upload file in hand before arrival, the expected ready time for each envelope can be computed at request time as: van's expected return to hub + reconciliation time + (assembly queue time if required) + sorting time. Where the file is late or missing (§5.1.1), geocoding cannot have run ahead of the bag and joins the sequence after reconciliation, in §5.1.1's order — open, key in, then geocode: van's expected return to hub + reconciliation time + geocoding time + (assembly queue time if required) + sorting time. Such an envelope cannot be computed at request time, only on arrival.
```

Two consequences worth stating plainly, because they are the operational content
of the change and not bookkeeping:

- **Assembly demand is not known in advance for a late-file bag.** §5.2.3 says
  "since the upload file arrives early, the clean room knows its day's workload
  before the bags do". For this bag it does not, so its assembly work joins the
  queue at geocoding rather than at file receipt. Where that leaves it in the
  queue is not stated here: §5.2.3 gives the clean room no discipline, so
  whether a late arrival waits behind work already scheduled or is ordered by
  priority is undetermined by the spec and left to §8.
- **"Computed at request time" fails**, and §9.1's own row says so more
  narrowly still — `expected_ready_at` is "Computed at upload-file receipt".
  For a missing file there is no such moment, so the row needs the same repair:

```diff
-| expected_ready_at | datetime | Computed at upload-file receipt; refined as the envelope progresses; actual time once Ready |
+| expected_ready_at | datetime | Computed at upload-file receipt, or on arrival where the file was late or missing (§5.1.1); refined as the envelope progresses; actual time once Ready |
```

## 4. §5.2.2 — one clause

```diff
-Envelopes whose upload file carried only a zip-code centroid have their delivery address geocoded. Because the file normally precedes the bag, this step runs **before arrival** in the usual case, so geocoding is off the critical path. Low-confidence results are held and flagged (§3.2).
+Envelopes whose upload file carried only a zip-code centroid have their delivery address geocoded. Because the file normally precedes the bag, this step runs **before arrival** in the usual case, so geocoding is off the critical path. Where the file is late or missing (§5.1.1) it runs after reconciliation instead, and is on the critical path. Low-confidence results are held and flagged (§3.2).
```

## 5. §5.2.6 — the first node's parenthetical is false for the exception

```
Requested (upload file received; geocoded and pre-sorted) → Collected → …
```

§5.1.2's stage 1 is the customer indicating bags are ready, recording counts
**from the manifest**. That does not require the upload file — the manifest is
physically attached to the bag, and the file is submitted separately. So an
envelope can be Requested with no file received, and the parenthetical asserts
otherwise.

```diff
-Requested (upload file received; geocoded and pre-sorted) → Collected → Received at hub → Reconciled → [Assembled] → Sorted → Ready
+Requested (usually: upload file received, geocoded and pre-sorted — §5.1.1's exception defers both to after Reconciled) → Collected → Received at hub → Reconciled → [Assembled] → Sorted → Ready
```

**This adds no state and no edge.** The graph is unchanged; a late-file envelope
walks the same path at the same nodes. CLAUDE.md makes transitions not listed
in §5.2.6 illegal, so it matters that none is being added — what is wrong is the
annotation on the first node, not the machine.

## 6. What is *not* a spec change: the geocoding rate

§5.2.5 already asks for it, and has since before this proposal:

> Processing throughput per hour for reconciliation, **geocoding**, assembly and
> sorting are needed to compute expected ready times. *[Open Question 4.]*

Open Question 4 (line 515) lists the same four. So a `GEOCODE_PER_HOUR` in
`ddn/assumptions.py` fills a declared `[TBD]` under CLAUDE.md's standing rule
and is **not gated by this proposal**. It does need the registry's own
discipline: marked **invented**, with a sensitivity note, and not fitted to
§10's "assembly clears 700 of the 900" — `docs/assumptions.md:58` warns that a
readiness figure computed from these rates is a property of the rates, and A9's
timing will be exactly that.

`docs/assumptions.md:76-77` is amended at the same time: geocoding has a rate
now, and the sentence explaining why it has none is retired to the usual case.

## 7. What lands in code once this is approved, and in what order

1. `GEOCODE_PER_HOUR` in `ddn/assumptions.py` + `docs/assumptions.md`
   (ungated per §6, but sequenced first because §2 below needs it).
2. `readiness.schedule` gains `late_files` (bag ids) and the fourth stage,
   between reconcile and assemble. `Readiness` gains the flag.
3. `test_a9` rewritten against A9's three clauses — slower order, later
   `expected_ready_at` than a same-time bag with a file, and the flag.
4. §13's ingest carries `file_received_at`; the API schema and its contract
   test follow §9.1.
5. Regression: `tests/test_peak_day_baseline.py` must be unchanged to the
   number. No fixture supplies a late file, so every envelope keeps today's
   path. No `Tally` or `Metrics` field is added, so that file's field-pin
   guards stay green — §8 question 3 is where that would change.

## 8. Open questions this proposal does not answer

1. **Does `late_ready` earn its place given `file_received_at`?** It is
   derivable (§2). The case for it is §5.1.1's own wording and the envelope's
   independence from its bag downstream; the case against is that §9.1 would
   then hold one computed boolean whose inputs are two tables apart.
2. **Is a late file a reconciliation discrepancy?** §5.2.1 lists "missing,
   extra, or damaged envelopes; broken seal" — all physical. A missing file is
   a data discrepancy with the same consequence (the bag is held up) and no
   home in §5.2.1's list. §11's `reconciliation_discrepancy_rate` would move if
   it counted.
3. **Does a late-ready envelope appear in §11?** A9 asks only that it be
   flagged. A count would be a thirteenth row and is not proposed here.
4. **Is there a cut-off after which a missing file stops the bag entirely?**
   §5.1.1 says the bag is processed in the slower order, which implies never.
   For a bag with no file at all, "key in" means keying in the manifest by
   hand, and §5.2.5 has no rate for that.

## What this proposal does not ask for

- **No geocoder.** `processing/` computes expected ready times; CLAUDE.md
  scopes it to that. The stage is a duration.
- **No change to §5.1.1.** It already states the rule completely. Everything
  here is the rest of the document catching up to it.
- **No change to the pickup side.** When the file arrives does not change which
  van collects the bag; e2e-1 §2.1's λ weighs assembly demand, which a late
  file makes unknown — that is §8 question 1's territory, not a routing change.
- **No new lifecycle state.** §5 above changes an annotation, not the machine.
