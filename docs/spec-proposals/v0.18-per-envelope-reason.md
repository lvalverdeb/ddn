# Proposed: §9.2 gives a reason per envelope, but names no rolled list to put one in

**Status:** proposal. Nothing here has been applied: §9.2's line-haul plan
still names a reason for transfers not carried and no list for the hub-origin
envelopes that were rolled. Written against **Draft v0.16** and re-checked
against **Draft v0.17**, where the asymmetry below is unchanged. v0.17 went to
the late-file exception while this waited, so the target — and this file's name
— is now **v0.18**.
**Date:** 23 September 2026
**Found by:** building Step 3 of `docs/plans/transfer-priority.md` — §5.3.2's
competition between hub-origin loads and transfers.

---

## Why this exists

Step 3 made hub-origin envelopes lose seats to transfers for the first time.
That created a new way for an envelope to miss tonight's van, and there was
nowhere in §9.2 to say so.

§9.2's line-haul bullet lists what a plan reports:

> **Line-haul plan:** per van, an ordered list of legs (from_facility,
> to_facility, departure, expected arrival) and per leg the loads on board
> (hub-origin package_ids by destination, transfer_ids, return package_ids)
> with total weight; **transfers not carried, with reason**.

A transfer that does not ride is reported with a reason. **A hub-origin
envelope that does not ride is not reported at all.** The asymmetry is not
deliberate — §5.3.2 now ranks the two against one 500 kg, so they lose seats
to each other symmetrically, and only one side of the loss is in the contract.

## What the code does instead

`linehaul.plan` returns two fields §9 never declared:

```python
rolled:  dict[str, tuple[str, ...]]   # facility_id -> package_ids left behind
reasons: dict[str, str]               # facility_id -> one reason
```

Both are keyed **by facility**, so a depot that rolls envelopes for two causes
in one night can report only one of them. Today's two causes are:

| reason | constant | true of |
|---|---|---|
| `not ready before the van's latest departure` | `plan.NOT_READY_IN_TIME` | an envelope whose `expected_ready_at` missed the departure |
| `the circuit is already at 500 kg` | `circuit.OVER_CAPACITY` | an envelope that was ready and lost its seat to a higher §8.1 score |

The implementation prefers `OVER_CAPACITY` when both occur, because a bumped
envelope *was* ready — `NOT_READY_IN_TIME` is not merely vaguer for it, it is
false. That is the best a per-facility field can do: the reason is true of at
least one envelope in the tuple it labels. It is still not what §9.2 asks for,
which is a reason per `package_id`.

## 1. §9.2 — the line-haul bullet names both sides

```diff
-- **Line-haul plan:** per van, an ordered list of legs (from_facility, to_facility, departure, expected arrival) and per leg the loads on board (hub-origin package_ids by destination, transfer_ids, return package_ids) with total weight; transfers not carried, with reason.
+- **Line-haul plan:** per van, an ordered list of legs (from_facility, to_facility, departure, expected arrival) and per leg the loads on board (hub-origin package_ids by destination, transfer_ids, return package_ids) with total weight; transfers not carried, with reason; hub-origin envelopes not carried, with reason, one per package_id.
```

"one per package_id" is the operative phrase. It is what the unassigned-
envelope bullet two lines above already says for the delivery solve —

> **Unassigned envelopes:** package_id; reason (…)

— and the line-haul roll is the same kind of fact about the same kind of unit.

## 2. The reason vocabulary has no entry for either line-haul cause

§9.2's closed list is:

> time / count / not ready by cut-off / low geocode confidence / SLA expired /
> in dispute / excluded by operations

Every entry is a *delivery-solve* reason. An envelope rolled to tomorrow's
line-haul is none of them:

- **not "not ready by cut-off"** — that is §5.2's hub cut-off, hours earlier
  and a different question. An envelope can clear the cut-off and still miss
  the van, which is exactly `NOT_READY_IN_TIME`.
- **not "count" or "time"** — those are motorbike capacity and route duration
  in the delivery solve. The line-haul bound is 500 kg of van, §7.1's own.

Two entries are needed, and they should be named for the stage:

```diff
-- **Unassigned envelopes:** package_id; reason (time / count / not ready by cut-off / low geocode confidence / SLA expired / in dispute / excluded by operations).
+- **Unassigned envelopes:** package_id; reason (time / count / not ready by cut-off / low geocode confidence / SLA expired / in dispute / excluded by operations / not ready before line-haul departure / line-haul van full).
```

## 3. What this changes in the code

`rolled` and `reasons` collapse into one field keyed by `package_id`:

```python
rolled: dict[str, str]   # package_id -> reason
```

This is a breaking change to `LinehaulPlan` and to §13.1's line-haul response,
which is why it is a proposal and not a patch. It is small — the two producers
are both in `plan()`'s facility loop and already hold the per-envelope lists
(`missed` and `loaded.bumped`) that the current code flattens into one tuple.
The flattening is the only thing being undone.

## What this proposal does not ask for

- **No new reason for transfers.** `circuit.py`'s three decline reasons
  already sit per `transfer_id`, which is what §9.2 asks for on that side.
  This proposal brings envelopes up to the transfers' standard, not the
  reverse.
- **No change to §5.3.2.** The competition is right; only the reporting of
  who lost it is missing.
- **No per-leg attribution.** Which leg an envelope would have ridden is not
  asked for and is not knowable for one that never boarded.
